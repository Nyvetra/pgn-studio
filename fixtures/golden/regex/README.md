# fixtures/golden/regex/

Supplemental golden fixtures for the platform regex engine behind
`pgn-extract`'s `=~` tag-criteria operator, added because **upstream's own
`test/` suite has zero `=~` coverage** (`grep '=~' test/` finds nothing -
verified during the Phase 0b engine-build design). `=~` is exactly the
code path that differs by platform: on Windows it is provided by the
vendored, statically-linked TRE v0.9.0 (`engine-src/upstream.lock`,
`engine-src/patches/tre-msvc/README.md`); on macOS it is the system libc.
Without fixtures like these, a broken or misconfigured regex engine could
ship silently - the upstream suite would still pass in full, because it
never exercises `=~` at all.

Also included: one fixture for the *other* regex call site in
`grammar.c`'s `check_for_odds` (a fixed internal pattern tested against
the `FEN` tag under `--odds`), independent of `taglines.c`/`lists.c`'s
`=~` machinery, so both of pgn-extract's two `<regex.h>` call sites have
dedicated coverage here even though `--odds` also happens to be covered by
upstream's `test-odds`.

## Provenance (architecture.md §4.3 "engine truth", matching
`fixtures/golden/README.md`'s policy for the merge fixtures)

Every `*-expected.pgn` file in this directory was generated by actually
running the real, checksum-verified, pinned `pgn-extract` sidecar built by
`scripts/build-pgn-extract.ps1` against the matching `*-in.pgn` +
criteria/flags, then reviewed by hand for correctness before being
committed. **None of them were hand-authored.** If a future engine or TRE
upgrade legitimately changes output formatting (not matching behavior),
regenerate them the same way and review the diff - don't patch bytes by
hand.

## Cases

See `manifest.json` for the machine-readable list consumed by
`scripts/verify-engine.ps1`. Summary:

| Case | Tag criterion | Proves |
|---|---|---|
| `literal` | `White =~ "Capa"` | Unanchored literal substring match |
| `anchors` | `White =~ "^Tal$"` | `^`/`$` anchors constrain to a full-string match (contrast with `literal`) |
| `bracket` | `Black =~ "^[BS]"` | Bracket expression `[...]`, and multi-game selection |
| `star` | `Event =~ "^AB*C$"` | Kleene star (zero-or-more) |
| `backref` | `Event =~ "^\(.\).*\1$"` | Escaped group `\( \)` plus backreference `\1` |
| `odds` | (`--odds` flag, no criteria file) | `grammar.c`'s independent fixed-pattern regex call site |

`backref` deliberately uses a backreference rather than GNU BRE
alternation (`\|`) to stay inside portable POSIX BRE - the design
explicitly calls out `\|` as a divergence risk between TRE, glibc, and BSD
libc regex implementations (design-01-engine-build.md §5), whereas
backreferences are core POSIX BRE (IEEE Std 1003.1-2001) that TRE targets
directly.

## Criteria file encoding - read before adding a new case

Criteria files **must** be UTF-8 **without a BOM**, with **LF** line
endings. A leading BOM makes `taglines.c`'s line reader silently treat the
entire file as containing zero valid criteria (no error, no games
matched, no games excluded - just quietly wrong). This directory's
`.gitattributes` coverage comes from the repository-wide `fixtures/**
-text` rule, which prevents git from ever converting these bytes on
checkout; when adding a new fixture, verify byte-for-byte
(`[System.IO.File]::ReadAllBytes(...)` and check for `0xEF 0xBB 0xBF` /
`0x0D 0x0A`) rather than assuming your editor got it right.

## Regenerating or extending

```powershell
$exe = "src-tauri/binaries/pgn-extract-x86_64-pc-windows-msvc.exe"
& $exe "-t$pwd/fixtures/golden/regex/<name>-criteria.txt" `
       "-o$pwd/fixtures/golden/regex/<name>-expected.pgn" `
       "--quiet" `
       "$pwd/fixtures/golden/regex/<name>-in.pgn"
```

Always pass arguments as an array element, never build a single command
string - decisions ledger finding V-6 documented PowerShell silently
mangling attached-form flags (e.g. `-o<path>`) when built via string
interpolation instead of passed as a literal array element. Use the
attached form for every short option that takes a value (`-t<path>`,
`-o<path>`, etc.) as a matter of policy, consistent with how this project
invokes the engine everywhere else: V-4 separately proved that `-e <path>`
(space-separated) fails *silently* with exit 0 and zero games extracted
for that specific flag - reason enough to never risk the separated form
for any value-taking short option, even where it has not been individually
proven to fail the same way.
